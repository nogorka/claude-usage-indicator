# Дизайн: опциональный сетевой fallback для VS Code

Дата: 2026-09-07
Статус: согласован в brainstorming + dev-team ревью, ждёт ревью пользователем перед writing-plans.

## Контекст и мотивация

Официальное расширение Claude Code для VS Code не вызывает `hooks`/`statusLine`.
Единственный источник данных проекта — `bin/claude-statusline.sh` → `~/.local/state/claude-usage/latest.json`
→ демон — в VS Code не наполняется никогда. Панель в этом сценарии постоянно
показывает «нет данных».

Проверена лестница дешёвых альтернатив, обе ступени пусты:

- `~/.claude/projects/*.jsonl` (локальные транскрипты сессий) не содержат окон
  `five_hour`/`seven_day`/`model_scoped` — только сообщения диалога.
- OTel-телеметрия Claude Code (`CLAUDE_CODE_ENABLE_TELEMETRY`) отдаёт токены,
  стоимость и метрики сессий, но не окна rate-limit, и требует внешнего
  OTLP-коллектора — не «локально».

Решение: строить opt-in сетевой fallback, сознательно принимая риск
«процесс с доступом к живому OAuth-токену делает исходящие запросы», при
условии изоляции и защит ниже. Это меняет зафиксированный в `docs/PLAN.md`
инвариант — правка инварианта входит в эту спеку (см. раздел «Правка
жёстких ограничений»).

## Архитектура

Два независимых компонента, связанных только общей схемой состояния (Ш0):

1. **Существующее, без изменений по существу** — `bin/claude-statusline.sh` →
   `latest.json` → демон в `src/claude_usage_indicator/`. Ноль сети, ноль
   credentials. Guard Task 6 продолжает грепать именно эти каталоги
   (`src/`, `bin/`, `scripts/`).

2. **Новое, opt-in, изолированное** — каталог `network-fallback/`, свой
   systemd user-юнит, свой install/uninstall-скрипт, свой guard.

Небольшая, но реальная правка существующего демона: `state.py` получает
функцию выбора между двумя снапшотами (см. «Правка существующего демона»).
Дев-тим-ревью подтвердило, что это не отдельная задача, а часть той же
фичи — без неё «fallback» описан словами, но не гарантирован кодом.

## Гейт поллера по свежести хука (закрывает главное найденное противоречие)

Дизайн до ревью описывал триггер как «сеть — только fallback», но поллер
физически стучался в сеть каждые 5 минут независимо от состояния хука:
публикация в панель зависела от свежести файлов, а сам факт сетевого
вызова — нет. Architect и Dev независимо назвали это разрывом между
намерением и механизмом.

Исправление: **поллер сам читает `latest.json` перед сетью**, до чтения
credentials.json и до открытия сокета.

- На каждом тике поллер читает только `updated_epoch` из `latest.json`
  (без парсинга остального содержимого).
- Если файл существует и `now - updated_epoch < STALE_THRESHOLD` — тик
  завершается немедленно: credentials.json не открывается, сеть не
  трогается. Это не только «не публикуем результат», а «не делаем сетевой
  вызов вообще».
- Порог берётся из текущей сигнатуры `bar.is_stale(snapshot, now_epoch,
  max_age_s=3600)` — те же 3600 секунд (час), что уже приглушают метку в
  панели (`docs/PLAN.md`: «данные старше часа — метка приглушается»).
  Значение переезжает в `state.py` как именованная константа
  `STALE_THRESHOLD_S = 3600`, чтобы поллер и демон читали одно и то же
  число, а не то, что `bar.is_stale` вынуждена дублировать локально.
- Если файла нет или он старше порога — поллер продолжает обычный путь
  (token_reader → client → adapter → запись).

Это не требует нового флага `--gated`: гейт — часть нормального поведения
поллера, не опция.

## Данные

Формат Ш0 (`five_hour`, `seven_day`, `model_scoped`, `extra_usage`) плюс
поле `source: "hook" | "network"`. Файл fallback — отдельный от `latest.json`,
в том же каталоге `~/.local/state/claude-usage/`, права `0600`,
например `network-fallback.json`.

Дополнительно, только в файле fallback (не в Ш0, не видно панели):
диагностические поля `last_attempt_epoch` и `last_reason` — см. раздел
«Reason-код деградации».

## Компоненты network-fallback/

- `token_reader.py` — читает `~/.claude/.credentials.json`, достаёт
  ровно `claudeAiOauth.accessToken` и `claudeAiOauth.expiresAt`. Никогда
  не возвращает и не логирует документ целиком (в файле помимо
  `claudeAiOauth` лежит `mcpOAuth` с секретами сторонних MCP-плагинов —
  Postman/Slack/Figma clientSecret и т.д. — их эта функция не касается
  даже мимоходом).
- `client.py` — единственное место с сетевым кодом. Один HTTPS GET на
  `https://api.anthropic.com/api/oauth/usage`, `Authorization: Bearer …`.
  Реализация через `http.client.HTTPSConnection` напрямую, а не
  `urllib.request` — `http.client` не читает `HTTPS_PROXY`/`https_proxy`
  из окружения вообще, поэтому вопрос «нужен ли явный
  `ProxyHandler`-опущения» снимается на уровне выбора модуля, а не
  дополнительной защитой поверх него. Хост захардкожен и сверяется перед
  соединением, редиректы (3xx) не читаются как успех и не проходят
  автоматически (`http.client` их и не выполняет сам), TLS-верификация
  включена (`ssl.create_default_context()`), таймаут ~5с.
- `adapter.py` — валидирует сырой ответ строго по структуре golden-фикстуры
  (см. «Контракт эндпоинта»), маппит в Ш0. Переиспользует валидацию из
  `state.py`, не дублирует.
- `poller.py` — точка входа: таймер 5 мин → гейт по `latest.json` →
  token_reader → client → adapter → атомарная запись. Ничего не бросает
  наружу; каждая ошибка на любом уровне — явный `try/except` конкретного
  исключения с присвоением reason-кода, не голый `except`.
- `logging_redactor.py` — токен по конструкции не долетает до вызовов
  логирования; редактор — вторая линия защиты, вырезает похожее на токен
  (включая base64-форму) из любой строки перед записью в лог/stderr.
- `systemd/claude-usage-network-fallback.service.in` — см. «Sandboxing».
- `install-network-fallback.sh` / `uninstall-network-fallback.sh` —
  отдельные от основных, идемпотентные, по образцу существующих.

## Sandboxing (исправлено по ревью)

Было предложено `ProtectHome=read-only`, что открывает сетевому процессу
весь `$HOME` на чтение — ssh-ключи, все чужие MCP-секреты из того же
`credentials.json`, произвольные пользовательские файлы. Architect указал
это как HIGH: слишком широкая поверхность для процесса с сетевым доступом.

Исправление:

```
ProtectSystem=strict
ProtectHome=tmpfs
BindReadOnlyPaths=%h/.claude/.credentials.json
ReadWritePaths=%h/.local/state/claude-usage
NoNewPrivileges=true
PrivateTmp=true
RestrictAddressFamilies=AF_INET AF_INET6
MemoryDenyWriteExecute=true
LockPersonality=true
CapabilityBoundingSet=
```

`ProtectHome=tmpfs` подменяет весь `$HOME` пустым tmpfs, `BindReadOnlyPaths`
пробивает в нём точечное read-only окно ровно на один файл,
`ReadWritePaths` — на каталог состояния. Процесс физически не может
прочитать ничего другого в `$HOME`, даже если бы попытался.

## Reason-код деградации (не меняет видимое поведение, только диагностику)

QA независимо от PM/Dev указала: тихий откат схлопывает все причины отказа
в одно состояние «нет данных», что делает матрицу отказов непроверяемой.
Пользовательское поведение остаётся прежним — **никакого видимого
состояния ошибки в панели**, — но внутри поллер пишет машиночитаемую
причину в свой собственный файл состояния:

```
expired_token | no_credentials_file | no_scope_403 | http_4xx | http_5xx |
tls_fail | timeout | redirect_blocked | schema_mismatch | ok
```

Поля `last_reason` и `last_attempt_epoch` лежат в `network-fallback.json`
рядом с `source`, панель их не читает и не показывает. Назначение — тесты
и ручная диагностика, не UI.

## Контракт `/api/oauth/usage` (было незафиксировано — MEDIUM из ревью)

Dev указал главный риск: не «сеть упала», а «ответ распарсился с другим
смыслом» (например, доля вместо процента) — панель тихо покажет 0% при
95%. Фикс — не эвристика доли-vs-процента (легитимный `used_percentage`
может быть меньше 1.0), а строгое требование структуры:

- В репозиторий коммитится golden-фикстура реального ответа —
  `network-fallback/tests/fixtures/oauth_usage_response.json`
  (отредактированная: без реальных значений аккаунта, но с реальной
  формой полей и типов).
- `adapter.py` валидирует **точное** соответствие ожидаемых ключей и
  типов этой форме. Любое структурное расхождение (отсутствующий ключ,
  несовпадающий тип, неожиданный вложенный объект) → `schema_mismatch`,
  без попытки угадать смысл.
- Тесты `adapter.py` включают мутированные копии фикстуры: другие имена
  полей, epoch как строка/миллисекунды/ISO, отсутствующие обязательные
  ключи — каждая обязана давать `schema_mismatch`, а не молчаливое
  0%/None.

## Правка существующего демона (state.py / bar.py / indicator.py / window.py)

Дев-тим-ревью показало, что «использовать fallback, если основной устарел»
сегодня не существует как код: порог свежести (`is_stale`) живёт в
`bar.py`, `read_state` возраст не проверяет. Решено (см. вопросы
пользователю) чинить это в существующих файлах, не выносить снаружи —
это часть той же фичи, а не отдельная задача.

- `state.py`:
  - `Snapshot` (dataclass) получает поле `source: Literal["hook", "network"]`.
  - Новая чистая функция `select_snapshot(hook: Snapshot | None, network: Snapshot | None) -> Snapshot | None`:
    выбирает по `updated_epoch` (не по mtime файла — это разные понятия
    свежести), при равенстве побеждает `hook` (источник истины по
    умолчанию), `None` только если оба отсутствуют.
  - `STALE_THRESHOLD` переезжает сюда из `bar.py`, чтобы им пользовались
    и демон, и поллер (гейт выше).
- `bar.py`: рендер не меняется по сути, только читает порог из `state.py`
  вместо локальной константы.
- `indicator.py` / `window.py`: читают `snapshot.source` только там, где
  нужен маркер `(сеть)` в строке возраста данных в меню/окне.
- Тесты: новые кейсы для `select_snapshot` (оба снапшота, только hook,
  только network, ни одного, равные `updated_epoch`); существующие тесты
  `bar.py`/`state.py` дополняются полем `source`; тесты `indicator.py`
  по-прежнему не покрывают GTK-рендер (долг #32, вне рамок этой фичи).

## Обработка ошибок

На каждом уровне — явная проверка конкретного исключения, ни одного
голого `except`. Любая ошибка → тик пишет `last_reason`, но не пишет
`limits`/`source`/`updated_epoch` — старый файл fallback (если был)
стареет штатно, гейт демона (`select_snapshot`) сам исключит его по
возрасту. Без агрессивных ретраев — следующая попытка через 5 минут.

## Тестирование

- Модульные тесты `token_reader`/`adapter`/`client` (сокет мокается,
  реальной сети нет), TDD, stdlib `unittest`.
- Guard, зеркальный к Task 6, но с собственной областью видимости:
  грепом по `network-fallback/` подтверждаем `socket|http\.client|ssl`
  только в `client.py`, `credentials|OAUTH` только в `token_reader.py`.
  Guard Task 6 по `src/`, `bin/`, `scripts/` не меняется.
- Самопроверяющий тест на утечку токена — расширен по находке QA:
  маркерный токен ищется не только в перехваченных stdout/stderr, но и
  (а) в записанном файле состояния `network-fallback.json`, (б) в
  сериализованных трейсбеках необработанных исключений внутри теста,
  (в) в **base64-форме** маркера (защита от кодирования при логировании
  бинарных данных). Отдельный тест: фикстура `credentials.json` для этого
  теста содержит decoy-секреты (`mcpOAuth.slack.token`,
  `mcpOAuth.figma.clientSecret`, `mcpOAuth.postman.apiKey` и т.п.) —
  тест обязан доказать нулевую утечку **и** decoy-секретов, не только
  своего accessToken.

## Правка жёстких ограничений (`docs/PLAN.md`, `README`)

PM и Architect указали одно и то же с разных сторон: текущая формулировка
«ноль сети / ноль credentials» в README и `docs/PLAN.md` читается как
безусловная гарантия всего репозитория, что после этой фичи станет
буквально неверным. Решено (см. ответ пользователя) — переформулировать
инвариант здесь, не выносить fallback в отдельный репозиторий.

Новая формулировка (заменяет текущие §1–2 «Жёсткие ограничения» и
критерий приёмки №8 в `docs/PLAN.md`):

> **Инвариант — свойство установки по умолчанию, не всего репозитория.**
> Установка по умолчанию (`install.sh`) не делает ни одного сетевого
> запроса и не читает credentials ни из одного файла в `src/`, `bin/`,
> `scripts/` — это подтверждается гвардом `tests/test_network_guard.py`
> (область не меняется).
>
> Дополнительно, отдельным опциональным шагом
> (`install-network-fallback.sh`, не входит в `install.sh`), можно
> установить сетевой fallback для сценариев без hook/statusLine (VS Code).
> У него собственная модель угроз (см. этот документ, раздел
> «Sandboxing»), собственный guard с собственной областью видимости
> (`network-fallback/`), и он не меняет гарантии установки по умолчанию.

README получает отдельный раздел «Опциональный сетевой fallback (VS Code)»
с этой же моделью угроз — не в одном абзаце с «ноль сети», а как явно
помеченный второй профиль установки. Точная правка текста README и
`docs/PLAN.md` — задача исполнителя плана (`writing-plans`/
`subagent-driven-development`), не этой спеки.

## Не переоткрывается без веской причины

- Изоляция каталога/юнита/install-скрипта от `src/claude_usage_indicator/`.
- Интервал 5 минут.
- Тихий откат к «нет данных» как видимое пользователю поведение (только
  внутренний reason-код меняется).
- Чтение только `accessToken`, никогда `refreshToken`, никакого
  refresh-flow.
- Эндпоинт только `/api/oauth/usage`, без fallback на `/v1/messages`.

## Открытые допущения

- Точная структура golden-фикстуры `/api/oauth/usage` требует одного
  реального вызова с личным аккаунтом архитектора для снятия формы ответа
  (значения потом редактируются) — это ручной шаг вне автоматизации,
  выполняется один раз при реализации.
