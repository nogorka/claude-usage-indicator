# Второй профиль Claude Code на одной машине

Проза к визарду `setup-second-profile.sh`. Здесь «зачем» и риски, в визарде — «как».
Меняется процедура — правятся оба файла одним коммитом.

## Зачем

Две подписки Claude на одной машине. Сегодня переключение между ними — полный
логаут и логин заново, а логаут сносит вместе с аккаунтом ещё и 15 OAuth-логинов
MCP-серверов, которые лежат в том же файле. Второй профиль убирает и то и другое:
аккаунты живут в разных каталогах, переключение — это переменная окружения.

Индикатор загрузки (план `docs/superpowers/plans/2026-09-10-multi-profile.md`)
рассчитывает, что второй профиль уже существует. Эта процедура — его предусловие.

## Механизм

`CLAUDE_CONFIG_DIR` — документированная переменная Claude Code: она уводит каталог
состояния из `~/.claude` в любой другой. Учётные данные, история и переписка
становятся своими у каждого профиля; всё остальное визард симлинкает обратно в
`~/.claude`, чтобы харнесс — скиллы, агенты, хуки, настройки, журнал — оставался
один, а не расползся в две расходящиеся копии.

Раскладка после процедуры:

```
~/.claude/                     рабочий профиль, он же дом общей части
~/.claude-personal/            второй профиль
├── .credentials.json          своё: аккаунт + перенесённые логины MCP
├── .claude.json               своё: появится при первом запуске
├── projects/, sessions/, …    своё: переписка и состояние сессий
├── CLAUDE.md -> ~/.claude/CLAUDE.md
├── skills/   -> ~/.claude/skills/
└── …                          симлинки на общее
```

## Что нужно под рукой

- Почта и пароль **второго** аккаунта Claude. Визард их не спрашивает: вход идёт
  в браузере, скрипт не видит ни одного символа.
- Никаких других секретов. Токены MCP переносятся файлом, вводить их не нужно.

## Шаги и откаты

| Шаг | Что делает | Обратимость | Откат |
|---|---|---|---|
| 0 | Проверки и страховочная копия `~/.claude/.credentials.json` | обратим | копия удаляется на шаге 6 |
| 1 | `mkdir -m 700 ~/.claude-personal` | обратим | `rmdir ~/.claude-personal` |
| 2 | Симлинки общей части | обратим | удалить перечисленные симлинки, визард печатает готовую команду |
| 3 | **`claude auth login` во второй профиль** | **необратим** | `CLAUDE_CONFIG_DIR=~/.claude-personal claude auth logout` |
| 4 | Перенос 15 логинов MCP в новый профиль | обратим | вернуть `~/.claude-personal/.credentials.json` из бэкапа `.bak-<штамп>` |
| 5 | Сверка обоих профилей | только чтение | — |
| 6 | Удаление страховочной копии | обратим до удаления | — |

Полный откат всей процедуры: логаут второго профиля плюс удаление каталога
`~/.claude-personal` — точная команда печатается визардом в конце.
Рабочего профиля процедура не касается — визард проверяет это дважды, по организации
и по числу логинов MCP, и останавливается с командой восстановления, если не сошлось.

## Решения и допущения

**Что осталось своим у профиля.** Владелицей решено «симлинкать всё общее, своими
оставить только `.credentials.json`, `.claude.json`, `projects/` и историю». Визард
это решение расширил, и вот чем:

- *Состояние живых сессий* — `sessions/`, `session-env/`, `session-data/`,
  `shell-snapshots/`, `ide/`, `paste-cache/`, `debug/`, `file-history/`. Два профиля
  работают одновременно; общие PID-локи и снапшоты означают, что одна сессия видит
  чужой процесс.
- *Расход и лимиты* — `policy-limits.json`, `telemetry/`, `metrics/`, `usage-data/`,
  `cost-tracker.log`, кэши состояния MCP. Они привязаны к аккаунту; общий
  `policy-limits.json` отравил бы ровно тот индикатор, ради которого всё затевалось.
- *Склады конфигов MCP* — `mcp.json` и `mcp-configs/`. Claude Code их не читает
  (серверы приходят из плагинов), а внутри лежат литеральные токены сторонних
  сервисов вида `JIRA_API_TOKEN`. Копировать секреты во второй профиль без нужды не
  стоит.
- *Машинные кэши и `.git` самого `~/.claude`* — второй профиль не рабочая копия
  репозитория харнесса.

Всё, чего нет в этом списке, симлинкается. Визард печатает оба списка целиком до
того, как что-либо создаст: решение видно глазами, а не спрятано в коде.

**Перенос логинов MCP.** Переносятся все 15 — решение владелицы, принятое против
рекомендации. Ключи `claudeAiOauth` и `organizationUuid` во втором профиле не
трогаются: переезжает только `mcpOAuth`.

## Известные ограничения

1. **`.claude.json` под `CLAUDE_CONFIG_DIR` — единственный непроверенный запуском
   факт.** Что переменная уводит не только каталог состояния, но и `.claude.json`,
   установлено чтением строк установленного бинарника (`process.env.CLAUDE_CONFIG_DIR||…`),
   а не прогоном: запускать сессии на почти исчерпанном недельном лимите было нельзя.
   Визард проверяет это сам после логина и останавливается, если конфигурация
   окажется общей.

2. **Часть хуков харнесса пишет в `~/.claude` жёстким путём.** `cost-tracker.js` и
   `session-activity-tracker.js` адресуют `~/.claude/metrics`, `~/.claude/sessions`
   и `~/.claude/session-data` абсолютным путём, минуя `CLAUDE_CONFIG_DIR`. Значит эти
   три каталога окажутся общими у обоих профилей, что бы визард ни симлинкал. На
   индикатор это не влияет — он берёт лимиты из stdin статуслайна, а не из `metrics/`.
   Долг: научить хуки читать `CLAUDE_CONFIG_DIR`.

3. **Копии токенов MCP не синхронизируются.** Когда один профиль обновит токен
   стороннего сервиса, копия в другом протухнет и сервис попросит авторизацию заново.
   Это следствие копирования, а не поломка.

4. **`shellcheck` на визарде не прогонялся** — он не установлен на машине, а ставить
   что-либо в систему в этой сессии запрещено. Проверка: `bash -n` (чисто) и чтение
   целиком глазами.

## После визарда

```bash
# второй профиль
CLAUDE_CONFIG_DIR=~/.claude-personal claude

# с подписью для индикатора
CLAUDE_CONFIG_DIR=~/.claude-personal CLAUDE_USAGE_PROFILE_LABEL='Личный' claude
```

Первый запуск второго профиля спросит тему оформления и доверие к рабочим каталогам —
это ожидаемо: `.claude.json` у него свой и пустой.

Дальше переключение берёт на себя индикатор: пункты меню в трее по плану мультипрофиля.
